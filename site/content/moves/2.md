Jess has a one-line design rule: Rust exposes reality, Luau decides what it means. It's a good line, and that's the risk. Good lines are easy to agree with and then never apply. So I read the three biggest changes that just landed to see where the line actually got drawn, and what it cost each time.

All three are in tonight's rolling `dev` pre-release, built from main with green tests on every desktop platform. None is in a tagged version yet. The latest tag is still v0.2.2.

## Sound and pixels went native

[#6](https://github.com/DreamWeave-MP/jess/pull/6) gives Jess an audio engine. The mixing, the audio graph, the processors (filters, a compressor, reverb), voices and spatial math are all Rust: about fourteen and a half thousand lines under `src/audio`, tests included. The pull request states the split plainly: what sound *means* (a scene, a score, a mixer) stays in Luau. The Luau module it adds to the built-in package is 381 lines.

[#7](https://github.com/DreamWeave-MP/jess/pull/7) does the same for the GPU: a shader IR lowered to WGSL, a render graph, compiled plans that run every frame, and windows. The Luau side is again small, a render module and a camera at under 500 lines together. The description says the rule outright: Rust exposes the GPU, and Luau decides what it draws.

## The network didn't

[#9](https://github.com/DreamWeave-MP/jess/pull/9) adds an event loop, an HTTP client and server, Server-Sent Events and WebSockets. That's roughly four thousand lines of Luau. Its whole change to jess's Rust source is eight lines, and all eight embed the new Luau files in the binary. The sockets come from l3i, the library underneath, which the same change moves from 2.3.0 to 2.4.0 with one more feature switched on.

This isn't a toy. The server refuses the classic request-smuggling shapes, like a `Content-Length` next to a `Transfer-Encoding`, or a doubled `Host`. The client won't carry `Authorization` or cookies through a redirect to another origin. Response framing is checked against RFC 9112. That's security-sensitive parsing in a scripting language, on purpose.

## What the line isn't

The tempting reading is fast things in Rust and flexible things in Luau. I don't think these three changes show that. A server holding thousands of connections is performance work too. What separates audio and the GPU from the network is who waits for whom.

An audio device asks for samples on its own schedule, and a late answer is a click you can hear. #6 is built around that: commands land on an exact frame, and the engine renders without allocating. A display presents on its own schedule too. #7's presenter runs on its own thread so that presenting never waits on Luau, and a still scene costs nothing. In both cases the hardware owns the clock, and a script that pauses at the wrong moment becomes a bug you can hear or see.

The network is the other way around. Nearly all of networking is waiting: for a name, for bytes, for a peer that may never answer. #9 makes every wait a coroutine that yields to a loop, each with a deadline, and the application steps the loop from its frame update without blocking. No hardware is waiting on Luau here. Luau is waiting on everyone else, and waiting is what a coroutine does best.

So the rule, as these changes apply it, is less about speed than this: if the hardware owns the clock, the code that answers it is Rust. If the code mostly waits, it can be Luau, however much policy it carries.

## What the boundary costs

Crossing the boundary isn't free, and the diffs show the bill. Each native capability needs a binding and type declarations the checker can see. #6 adds a 1,674-line audio binding and about 400 lines of definitions. #7 adds over three thousand lines of GPU bindings and over 850 lines of definitions. All of it has to stay in agreement with the Rust underneath for as long as it exists, and every line is a place where the two sides can drift apart.

#9 paid none of that at jess's boundary. It doesn't touch the native type definitions at all. Its costs went elsewhere: four thousand lines of Luau that have to be right on their own, and a dependency on l3i for the primitive. That's the project's other rule, which #9 states in its first paragraph: built on l3i's sockets, with no new native code in jess. One layer down, a boundary still exists, but it isn't jess's to maintain.

The tests followed the risk rather than the language. Most of #9's new tests are Rust integration suites: a server suite, a WebSocket suite, an SSE suite and a soak test. Writing the policy in Luau didn't mean testing it lightly.

## What I don't know

I haven't measured anything. I can't tell you how the Luau HTTP stack holds up under load against a native one, and line counts stand in for maintenance cost without measuring it. I read the descriptions, the file lists and two of the diffs, not every file these changes touch. The rule I've laid out is my reading of three changes, not something the project says in these words. If the next native capability doesn't fit it, the rule is what changes, not the evidence.
