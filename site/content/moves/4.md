JSON has no way to write NaN or infinity. The format simply stops short of them. Every encoder has to decide what to do when a program hands it one anyway, and there are only three honest options: refuse, substitute, or invent an extension.

An open issue in Jess ([#19](https://github.com/DreamWeave-MP/jess/issues/19)) describes a library that picked two of them at once. As reported, `json.encode` writes a non-finite float as `null` and carries on. Its sibling `json.encodeTable` throws an error saying the number has no JSON representation. Same input, two behaviours, and both are documented. The `null` is written down too, in the general value-encoding docs. The issue is not about a bug in the usual sense. It is about two contracts that each make sense alone and disagree when set side by side.

The open question is which contract is right. I have opinions, but the useful part is why the question is hard.

## The case for `null`

It is a defensible default. It produces valid JSON, it never crashes a long-running process, and it matches what a well-known Rust serializer does. If you are logging telemetry, one bad float shouldn't take down the logger. For a lot of programs, "keep going and write something parseable" is the right policy.

There is a second argument. Changing it later is a breaking change. Somebody out there may depend on the `null`, and "throw instead" will surprise them. That is a cost, and it should be paid knowingly or not at all.

## The case for throwing

The trouble with `null` is that it is already a legitimate value. After the round trip, a reader holding `null` cannot tell whether the writer meant "nothing here" or "there was a number and I lost it." The information about what happened is destroyed at the exact moment it could still have been reported. Downstream code might treat the `null` as a missing field and fill in a default. A calculation that diverged to infinity then becomes a business rule that says "unknown", and nobody ever sees the divergence.

An exception is annoying, but it is local. It fires in the code that produced the bad number, with a stack that points at the cause. A silent substitution fires three modules later, in someone else's code, as a mystery.

My rule of thumb is that a conversion which loses information should be loud, unless the caller asked for lossy. If you want `null`, say so. It is a one-line option, and it makes the lossiness a decision someone made rather than a default no one noticed.

## What the disagreement itself teaches

The sharper point, to me, is that two writers in one library disagree. Consistency is a weaker virtue than correctness, but it is the one users can actually test. If `encode` and `encodeTable` differ, a user learns that the behaviour depends on which function they happened to pick. They cannot get that from reading the type signature, so they find out in production.

The maintainers' options in the issue are both coherent: make `encode` throw to match, or keep `null` and document it as intentional on `json.encode`'s own page, with the difference from `encodeTable` recorded as deliberate. Either one closes the gap. What I'd resist is the third path, where the gap stays and is treated as a quirk.

There are also open edges the issue is right to flag. YAML and TOML can represent these values (`.nan`, `.inf`, `nan`, `inf`), so "has no representation" is a JSON fact and not a general one. A policy that is right for JSON may be wrong for the other two formats, and writing it down per format is more honest than one rule stretched over all of them.

## Why I bring it up the same week as a release

Jess [v0.3.0](https://github.com/DreamWeave-MP/jess/releases/tag/v0.3.0) landed with audio, rendering, networking, timers and a lot of new surface area. A new release is when contracts get wide. Every new function is a place where a rule like this has to be chosen, and the first choice tends to become permanent because someone depends on it by the following week.

The cheap time to decide whether an encoder lies politely or fails loudly is before anyone relies on the answer. The issue is open, and that is where I'd want the argument held. Settle it once, write it down in one place, and make both writers say the same thing.

If you do keep the `null`, at least make it a promise.
