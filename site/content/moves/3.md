Ask an engineer about build systems and you'll hear a complaint, usually about CMake. Mine is narrower. Build systems handle the inside of a language well and its edges badly, and nearly everything that hurts happens at the edges.

## Inside, the build system knows the truth

Cargo is pleasant for Rust because it can see everything that matters: every crate, its version, its features, its edition, and which test belongs to which target. When it decides what to rebuild, it's reasoning about facts it owns. Most single-language tools work this way. Inside one language, a build system is a database with a scheduler bolted on.

The trouble starts when one compiler has to hand work to another.

## At the edge, it prints instructions and hopes

Jess's recent audio work ([#6](https://github.com/DreamWeave-MP/jess/pull/6)) is a tidy example. Most of it is Rust. The part that talks to a sound device goes through miniaudio, a C library vendored exactly as upstream publishes it. To build that, the change adds a 33-line build script. It compiles one C file against the vendored header, turns off warnings because those are upstream's to fix, and then holds a small table:

- Linux links `dl`, `pthread` and `m`.
- Android links `dl` and `m`, because Bionic puts threads in its C library.
- macOS and the BSDs link `pthread` and `m`.

Cargo knows none of this, and nothing can teach it. A build script is a program whose output is instructions Cargo agrees to follow. The knowledge in that table came from someone who got bitten on each of those platforms.

The same change also sets `CC = "clang"` in the project's Cargo config (`clang-cl` on Windows), next to the `CXX` lines that were already there. The comment explains why: on many Linux hosts the system `cc` is GCC, and the Luau runtime under Jess is never built with GCC. The Linux target already builds with `-Clinker-plugin-lto` and links with clang and lld. Link-time optimization across languages only works when the Rust and C sides agree on the compiler underneath. So the build is keeping three toolchains on one version of the truth, and the tool it uses is environment variables.

This is the part I find most instructive. Cargo's unit of truth is the crate. The thing that has to agree here is the toolchain, which belongs to the whole machine doing the build. Cargo doesn't apply a dependency's config to the crates that use it, so a library that needs these settings can't bring them along, and every consumer has to copy them. The build system's model doesn't match the shape of the problem, and the gap gets filled with comments and copied lines.

## About CMake

Which brings me, as tradition requires, to CMake. It earned its reputation: variables leak across scopes, two models overlap (directory properties and targets), and you can't tell which style a file uses without reading all of it. But a fair share of the ugliness comes with the job. C and C++ have no single compiler, no package format, and no agreed way to say "link the threading library." Cargo only visits the edge inside build scripts; CMake lives there full time. It's a language about compilers because nothing else in its world is stable enough to stand on. I'd still rather debug it than rewrite it, and I'd rather not need it at all.

## The best edge is one you cross once

You can't remove the edges. You can choose who crosses them, and how often.

Jess's packed workspaces ([#1](https://github.com/DreamWeave-MP/jess/pull/1)) make that choice on purpose. A workspace freezes into one `.jsw` file with each package pinned to its content digest. With `--runtime`, it becomes a standalone executable: a prebuilt jess for Linux, Windows or macOS carrying the packed workspace byte for byte. Any platform's jess can serve as the runtime, so one machine can build every platform's executable without a compiler. For someone writing an application, the whole build system is one pack step.

The edges didn't go away. They moved to the people who chose to take them on. macOS code signing seals a file, and bytes appended after the seal can't be signed again, so a macOS jess reserves a section of its own, and packing grows it, shifts everything after it, and signs the result again ad hoc. Windows CI found that a scratch file had to be closed before packing could replace it. Review found that PE headers have to be read wherever the header offset points, because a stub longer than 4 KiB had hidden a signature. All of that gets paid once, in Jess's own release pipeline. Its latest run on `main` ([2026-10-31](https://github.com/DreamWeave-MP/jess/actions/runs/41158946629)) built for Linux, Windows, macOS on ARM and Intel, and PortMaster, tested and linted on four of them, and passed the format, audit, MSRV and packaging checks. Everyone downstream just gets a file.

## So, my opinion

Judge a build system by what it does at the edge. Inside one language, most of them are fine, and the differences come down to taste. A good build and a miserable one differ in how many language boundaries each person has to cross, and in whether the knowledge for each crossing is written down where the next person will find it. That table of `dl`, `pthread` and `m`, with its one-line note about Bionic, is worth more to me than most build-system features. It's a map of the edge, drawn by someone who walked it.
